## 4. Сопоставление полей

Целевая модель — из раздела 13 ТЗ. Сопоставление с колонками таблицы будет сделано после доступа (P2). Шаблон для каждого поля: лист → столбец → поле Supabase → тип → нормализация → валидация → обязательность → поведение при пропуске.

Правила уже сейчас (из ТЗ, не зависят от таблицы):
- ключ сопоставления — SKU поставщика, если он уникален; иначе правило согласуем отдельно; название не ключ;
- `supplier_price` (закупка) никогда не уходит на клиент;
- `compare_at_price` (старая цена) — только при подтверждённом основании;
- фото привязываются к SKU, без «заглушек» с чужих моделей.

## 5. Схема Supabase (предложение)

Отдельный проект Supabase (регион eu-central-1). Таблицы по разделу 13: `products`, `product_media`, `orders`, `order_items`, `order_status_history`, `integration_outbox`, `admin_audit_log`, `catalog_sync_runs`, `admin_users`, плюс `idempotency_keys` (или уникальный `orders.idempotency_key`).

Ключевые ограничения:
- `products.supplier_sku` UNIQUE, `slug` UNIQUE, цены `numeric(12,2) CHECK (>= 0)`, валюта `CHECK = 'UAH'`;
- `orders.public_reference` UNIQUE (короткий, неугадываемый, напр. `EL-7K3Q9`), `orders.idempotency_key` UNIQUE;
- статус — enum + функция-переходник `transition_order_status()` с проверкой допустимых переходов и записью в историю в одной транзакции;
- создание заказа — одна SQL-функция (RPC) `create_order(...)`: пересчёт цены из `products`, snapshot, позиции, outbox — атомарно;
- RLS: anon читает только опубликованные товары/медиа (через view без закупочной цены); заказы, история, outbox, аудит — только service role. Тесты RLS обязательны.

## 6. План синхронизации каталога

Google Sheets API (сервисный аккаунт) → `/api/integrations/catalog-sync` (Vercel, только сервер) → нормализация → валидация → diff → запись в Supabase.

- Режимы: **dry run/preview** (отчёт без записи) и **publish**; ручной запуск из админки + Vercel Cron (предложение: раз в 1 час в сезон; без обещаний real-time).
- Блокирующие аномалии (пороги конфигурируемые): пропало > 20% товаров; цена 0/пусто у > 0 товаров; изменение цены > 50%; дубль SKU; не `UAH`; изменился набор заголовков.
- Пропавшая строка → `status = unpublished`, не удаление.
- Ошибка API → остаётся последняя валидная версия, запись в `catalog_sync_runs`, уведомление в Telegram.
- Политика актуальности: если последняя успешная синхронизация старше N часов (предложение: 48 ч), оформление заказа требует ручного подтверждения цены менеджером (статус `confirmation_pending` и так это делает) — обсудить.
- Блокировка параллельных запусков: `pg_advisory_lock` или строка-замок в `catalog_sync_runs`.

## 7. Заказы и статусы

Checkout: имя, телефон (+380 маска), город, отделение (если НП — по согласованию автоподсказка через API НП позже), количество, комментарий. Цена — только с сервера.

Алгоритм — ровно раздел 9 ТЗ, внутри одной RPC-транзакции; idempotency key генерируется в браузере при открытии формы.

Статусы — предлагаю набор ТЗ без изменений: `new → confirmation_pending → confirmed → processing → shipped → delivered → purchased`, ветки `cancelled`, `unclaimed`, `returned`. Таблица допустимых переходов — в коде и в БД. **Нужно подтвердить по реальному процессу (P6).**

## 8. Telegram и админка

- Бот: новый токен (после отзыва), webhook `/api/webhooks/telegram` с `secret_token`, whitelist `TELEGRAM_ALLOWED_USER_IDS`, проверка перехода статуса на каждом нажатии, повторные callback — идемпотентны.
- Уведомление: номер, время, товары, сумма, статус, ссылка в админку. Имя/телефон — только если чат закрытый и вы этого хотите (решение).
- Доставка через `integration_outbox` + Vercel Cron (раз в минуту) с ограниченными ретраями; первую попытку делать сразу после commit (через `after()`/waitUntil), чтобы уведомление приходило за секунды.
- Админка `/admin`: вход через Supabase Auth (magic link по email из `admin_users`), список/фильтры/поиск заказов, карточка заказа с историей и UTM, статус outbox и повторная отправка, страница синхронизации каталога с preview/запуском. Аудит каждого действия.

## 10. Тестирование и развёртывание

- Unit (Vitest): нормализация/валидация каталога, пороги аномалий, переходы статусов, расчёт суммы.
- Integration: RPC `create_order` на локальном Supabase (идемпотентность, snapshot, подмена цены клиентом), RLS-тесты (anon не видит заказы и закупку), Telegram webhook (чужой user ID, повторный callback).
- E2E (Playwright, мобильный viewport): UTM → каталог → свайп → CTA → checkout → успех → повторная отправка не создаёт дубль.
- Vercel: Preview использует отдельную ветку/проект Supabase и тестовый чат Telegram, Meta `test_event_code`; production — только после чек-листа раздела 27.
