# LANDING_SPEC.md
# Полное ТЗ интернет-магазина новогодних ёлок

Версия: 3.0  
Рынок: Украина  
Основной трафик: Meta Ads (Facebook/Instagram)  
Приоритет: мобильные устройства, прибыльные выкупленные заказы, надёжная обработка и измеримая оптимизация конверсии.

Стек: Next.js + TypeScript, Vercel, Supabase Postgres, Google Sheets API, PostHog, Telegram Bot API, Meta Pixel + Conversions API; GA4 — при необходимости.

---

## 0. Главная цель и источники истины

Создать быстрый mobile-first магазин новогодних ёлок: посетитель быстро выбирает товар, рассматривает фотографии, видит достоверные характеристики и оформляет заказ без регистрации. Владелец получает заказы, управляет статусами, контролирует каталог, атрибуцию и фактическую прибыльность рекламы.

| Данные | Источник истины |
|---|---|
| Исходные данные поставщика | Google Sheets |
| Опубликованный каталог | Supabase |
| Состав, цена и условия оформленного заказа | Неизменяемый snapshot в Supabase |
| Статусы и история заказов | Supabase |
| Действия администратора | Supabase audit log |
| Поведение пользователей | PostHog |
| Рекламные конверсии | Meta Pixel/CAPI с учётом ограничений атрибуции |
| Расходы на рекламу | Подтверждённый импорт/данные рекламного кабинета |
| Оперативные уведомления | Telegram |

Google Sheets — единственный исходный источник каталога. Google Docs не используется. Supabase — рабочая база каталога, заказов и истории. Telegram не является базой данных; PostHog, Meta и GA4 не являются финансовым источником истины.

Запрещено выдумывать товары, цены, характеристики, наличие, отзывы, скидки, сроки доставки, юридические условия, фальшивые таймеры/дефицит или старые цены. Не доверять цене из браузера. Не считать отправленный заказ выкупленным. Не считать страницу успеха доказательством заказа. Не допускать дублей. Не помещать секреты в клиентский код/Git. Ошибки аналитики не должны блокировать checkout. Ошибка Google Sheets не должна удалять каталог. Неизвестные данные помечать как неизвестные, не угадывать.

## 1. Инструкции для Claude Code

До разработки:
1. Прочитать этот документ целиком.
2. Изучить репозиторий, стек, зависимости, структуру, состояние Git и незакоммиченные изменения.
3. Изучить реальную Google Таблицу при наличии доступа.
4. Определить фактические листы, столбцы, SKU, цены, медиа, характеристики, формулы, дубликаты и пропуски.
5. Проверить существующие интеграции и переменные окружения, не выводя секреты.
6. Подготовить карту данных, архитектуру, список неизвестных и поэтапный план.
7. Не начинать массовую генерацию кода до аудита.

Не переписывать работающие части без причины и не добавлять библиотеки без оценки пользы/стоимости. После каждого этапа запускать проверки и сообщать, что действительно проверено. Согласование требуется для платных ресурсов, production-миграций с риском потери данных, удаления production-данных, массовых изменений каталога, реальных сообщений, изменений рекламы и необратимых действий.

При конфликте требований приоритет: безопасность/приватность → целостность заказов/финансов → проверка цены/наличия → фактические данные поставщика → непрерывность сайта → интеграции → аналитика → дополнительные CRO-функции.

## 2. Цели и KPI

Главные метрики: выкупленные заказы; выручка с учётом возвратов; маржинальный результат до рекламы и прибыль после рекламы; стоимость выкупленного заказа; доля подтверждения, выкупа, отмен и невыкупа; конверсия в созданный/подтверждённый/выкупленный заказ; маржинальный результат на посетителя; средний чек.

Диагностические метрики: CTR, CPC, CPM, просмотры каталога/товаров, взаимодействия с галереями, CTA, начало checkout, ошибки формы, время оформления, скорость сайта. Не оптимизировать только клики и сырые COD-заказы.

## 3. Архитектура

- **Next.js + TypeScript:** App Router, каталог, страницы товаров, checkout, страница успеха, информационные страницы, админка, серверная бизнес-логика, API, Telegram webhook, синхронизация.
- **Vercel:** production/preview, HTTPS, логи, окружения. Preview не меняет production-каталог, не создаёт рабочие заказы и не загрязняет production-аналитику.
- **Supabase:** каталог, медиа, статусы публикации, заказы, позиции, snapshots, история, атрибуция, outbox, журналы синхронизации и аудит.
- **Google Sheets:** источник поставщика; серверный импорт в Supabase. Не обращаться к таблице при каждом просмотре/заказе.
- **PostHog:** поведение, воронки, Session Replay, UX и эксперименты.
- **Telegram:** уведомления и разрешённые административные действия.
- **Meta Pixel/CAPI:** рекламные события и атрибуция с дедупликацией.
- **GA4:** дополнительная аналитика при необходимости.

## 4. Аудит Google Sheets и карта данных

До написания окончательного импортёра:
1. Получить доступ и изучить все относящиеся к каталогу листы.
2. Зафиксировать реальные названия листов и заголовки столбцов.
3. Определить формат строк, SKU, цены, валюту, наличие, характеристики, фото/видео, формулы и вычисляемые значения.
4. Найти дубли, пустые и некорректные значения.
5. Разделить публичные и внутренние поля.
6. Подготовить `docs/DATA_MAPPING.md`.

Не предполагать структуру заранее. Если доступа нет — запросить его, не придумывая данные.

Целевая модель товара может включать ID, SKU поставщика, название, slug, описание, характеристики, категорию, закупочную/розничную/сравнительную цену, валюту, наличие, медиа, порядок, статус публикации, время изменения источника и последней синхронизации. Это целевая модель, а не утверждение, что все поля существуют в таблице.

Для каждого поля документировать лист, исходный столбец, назначение, целевое поле, тип, нормализацию, валидацию, обязательность и поведение при отсутствии значения.

### Цена и идентификация
Разделять закупочную, розничную, сравнительную и итоговую цену заказа. Не подменять одну другой, не придумывать наценку/скидку. Неясную формулу выяснить до публикации. Скидка и старая цена допустимы только при подтверждённом основании.

Использовать стабильный ID. Если SKU уникален, использовать его для сопоставления. Если SKU отсутствует/дублируется — определить безопасное правило до автоматизации. Не использовать название как единственный ключ, если оно меняется или повторяется.

### Медиа
Проверять принадлежность фото/видео конкретному SKU, порядок, основное изображение, формат и доступность. Не смешивать модели и не подставлять случайное изображение при ошибке.

## 5. Синхронизация каталога

Схема: **Google Sheets → серверный импортёр → нормализация → валидация → Supabase → сайт**.

Импортёр поддерживает первоначальный/повторный импорт, сравнение изменений, выявление новых/изменённых/пропавших товаров, валидацию SKU/цен/наличия/медиа, Preview, dry run без публикации, отчёт, журнал, retry, уведомления, ручной запуск из админки и защиту от параллельных запусков.

Критические аномалии (массовое исчезновение, обнуление цен, дубли уникальных SKU, невалидная валюта, повреждённый формат) блокируют опасную публикацию. Пороги документировать и сделать конфигурируемыми.

Исчезновение строки не удаляет товар физически: использовать снятие с публикации/статус недоступности. Исторические заказы сохраняются. При повторном появлении восстанавливать запись только при подтверждённой идентичности.

При временной недоступности Google Sheets сохранить последнюю валидную версию, записать ошибку, уведомить администратора и повторить попытку. Не считать все товары удалёнными. Если цена/наличие конкретного товара не могут быть безопасно подтверждены по принятой политике актуальности, временно остановить оформление этого товара.

Частоту синхронизации выбрать с учётом лимитов API, объёма и реальной потребности. Не обещать real-time, если его нет.

## 6. Дизайн и мобильный UX

Mobile-first: быстрый первый экран, читаемые названия/цены, крупные элементы, удобная прокрутка, независимые галереи, минимум переходов, короткий checkout. Не перегружать карточки, не использовать тяжёлые анимации, навязчивые pop-up и длинный рекламный текст перед каталогом.

Показывать только подтверждённые условия оплаты/доставки/возврата, контакты и характеристики. Не добавлять фальшивые отзывы/рейтинги/заявления о популярности.

## 7. Главная и каталог

Маршрут `/`. Структура: первый экран, краткое предложение, каталог, помощь с выбором, доставка/оплата, FAQ, контакты, юридические страницы. Товары показывать достаточно рано.

Карточка: фото и горизонтальная галерея одной модели; название; актуальная розничная цена; реальная скидка при наличии; до трёх достоверных преимуществ; CTA «Заказать»; ссылка «Подробнее о товаре».

Вертикальный свайп двигает каталог, горизонтальный — фото внутри карточки. Галереи независимы; переключение фото не должно случайно открывать страницу товара.

«Заказать» открывает `/checkout` с ID/SKU; сервер заново проверяет цену и доступность. Цена из браузера недоверенная. «Подробнее о товаре» открывает `/product/[slug]`. Подробная страница не обязательна для готового к покупке посетителя.

Sticky CTA допускается как эксперимент, если не перекрывает контент/форму. Порядок товаров стабилен; сортировка/фильтры используют только реальные данные.

## 8. Страница товара и SEO

`/product/[slug]`: название, галерея, цена, подтверждённая скидка, описание, характеристики, комплектация при наличии, достоверное наличие, условия доставки/оплаты, CTA, возврат в каталог.

SEO: уникальные title/description, canonical, Open Graph, sitemap, robots directives, семантическая структура и Product structured data с фактическими значениями. Не добавлять фиктивные рейтинги/отзывы в structured data.

## 9. Checkout и создание заказа

`/checkout`. Без регистрации, минимум обязательных полей, удобная мобильная форма. Набор полей определяется реальными требованиями доставки/бизнеса. Возможные поля: имя, телефон, товар, количество, город, способ/данные доставки, необязательный комментарий. Не запрашивать ненужные данные.

До отправки показывать товар, количество, цену, сумму, подтверждённую скидку, известную доставку и итоговую сумму либо объяснение неизвестной части стоимости.

### Серверный алгоритм
1. Получить и валидировать форму.
2. Проверить idempotency key.
3. Получить товар из Supabase.
4. Проверить публикацию, актуальность цены и доступность.
5. Рассчитать сумму на сервере.
6. Создать публичный номер.
7. Создать заказ и позиции со snapshot названия, SKU, цены, количества и условий.
8. Сохранить допустимую атрибуцию.
9. Создать outbox-задания интеграций.
10. Сохранить критические записи согласованно в транзакции.
11. Подтвердить создание только после успешного commit.

Не выполнять внешние HTTP-запросы к Telegram/Meta/PostHog внутри транзакции. Повтор с тем же idempotency key возвращает тот же заказ. Новый осознанный заказ остаётся возможным.

Страница `/order/success/[publicReference]` показывает подтверждение только после сохранения, номер и следующий шаг. Не раскрывать персональные данные. Публичный номер не даёт доступ к полным данным заказа. Страница не создаёт заказ и не отправляет повторный Purchase при обновлении.

## 10. Статусы заказов

Предлагаемые статусы: `new`, `confirmation_pending`, `confirmed`, `processing`, `shipped`, `delivered`, `purchased`, `cancelled`, `unclaimed`, `returned`. Утвердить окончательный набор по реальному процессу.

`new` — создан; `confirmation_pending` — ожидает подтверждения; `confirmed` — подтверждён; `processing` — обрабатывается; `shipped` — отправлен; `delivered` — доставлен, если факт доступен; `purchased` — фактически выкуплен; `cancelled` — отменён; `unclaimed` — невыкуплен/неполучен; `returned` — возвращён.

`shipped` и `delivered` не равны `purchased`. Каждый переход проверяется и сохраняет старый/новый статус, время, инициатора, причину при наличии. История не удаляется. Возвраты и финансовые корректировки отражаются в отчётах.

## 11. Telegram

Уведомлять разрешённый административный чат о новых заказах: публичный номер, дата/время, товары/количество, сумма, статус и ссылка на защищённую админку. Персональные данные отправлять только если необходимы и чат защищён.

Кнопки: открыть заказ, подтвердить, в обработку, отправлен, выкуплен, отменить. Показывать только действия, допустимые для статуса.

Bot Token хранить на сервере. Проверять webhook, Telegram user ID, права на каждом действии, переход статуса и повторные callback. Вести аудит. Нельзя менять заказ только по публичному номеру.

Заказ сначала сохраняется в Supabase, затем уведомление доставляется через outbox. Сбой Telegram не блокирует checkout. Повторные попытки ограничены; ошибки видны администратору.

## 12. Админка

Маршруты `/admin`, `/admin/orders/[id]`, `/admin/catalog-sync`.

Функции: авторизация, список/поиск/фильтры заказов, детали и позиции, сумма, история, источник/UTM, состояние уведомлений, повторная отправка, статус синхронизации Sheets, ошибки импорта, Preview и ручной запуск синхронизации.

Проверять права на сервере для каждой операции, ограничивать доступ к персональным данным, защищать API и вести аудит. Telegram Mini App не входит в первый релиз.

## 13. Схема Supabase

Использовать миграции, индексы, ограничения и RLS. Это логическая схема; типы уточняются при реализации.

- `products`: `id`, `slug`, `name`, `supplier_sku`, `supplier_price`, `selling_price`, `compare_at_price`, `currency`, `description`, `attributes`, `availability`, `status`, `sort_order`, `source_updated_at`, `last_synced_at`, `created_at`, `updated_at`.
- `product_media`: `id`, `product_id`, `media_type`, `url`/storage path, `sort_order`, `alt_text`, `is_primary`, `source`.
- `orders`: `id`, `public_reference`, `status`, `customer_name`, `customer_phone`, `delivery_data`, `subtotal`, `discount_total`, `delivery_cost`, `total`, `currency`, UTM, допустимые рекламные идентификаторы (`fbclid`, `_fbp`, `_fbc` при наличии/основании), `created_at`, `updated_at`, `confirmed_at`, `shipped_at`, `purchased_at`, `cancelled_at`.
- `order_items`: `id`, `order_id`, `product_id`, `supplier_sku`, `product_name_snapshot`, `unit_price_snapshot`, `quantity`, `line_total`, `currency`.
- `order_status_history`: `id`, `order_id`, `old_status`, `new_status`, `changed_by`, `reason`, `created_at`.
- `integration_outbox`: `id`, `event_type`, `entity_type`, `entity_id`, `destination`, `idempotency_key`, `payload`, `status`, `attempt_count`, `next_retry_at`, `last_error_code`, `created_at`, `processed_at`.
- `admin_audit_log`: `id`, `actor_id`, `action`, `entity_type`, `entity_id`, `details`, `created_at`.
- `catalog_sync_runs`: `id`, `source`, `started_at`, `finished_at`, `status`, `items_read`, `items_created`, `items_updated`, `items_skipped`, `error_count`, `summary`.
- `attribution_touchpoints` (если требуется): `id`, `session_id`, `order_id`, `touch_type`, UTM, разрешённые рекламные ID, `created_at`.

Snapshot позволяет восстановить историю, даже если товар изменён/снят. Service-role key — только серверу. Публичные пользователи не получают доступ к заказам. RLS проверяется тестами. Схема меняется миграциями.

## 14. PostHog

События интерфейса: `catalog_view`, `product_card_view`, `product_detail_view`, `product_gallery_swipe`, `product_image_open`, `order_cta_click`, `product_details_click`, `checkout_started`, `checkout_field_error`, `checkout_validation_error`, `order_submit_attempt`.

События процесса: `order_created`, `order_confirmed`, `order_shipped`, `order_delivered`, `order_purchased`, `order_cancelled`, `order_unclaimed`, `order_returned`. Отправлять сервером после commit; для надёжной доставки — outbox/idempotency.

Допустимые свойства: `product_id`, `product_sku`, `placement`, `gallery_index`, `cta_location`, `experiment_id`, `variant`, UTM при допустимости, технические сведения в рамках приватности. Не отправлять имя, телефон, адрес, комментарий, токены и полный payload заказа.

Session Replay маскирует пользовательский ввод и чувствительные элементы. Если безопасное маскирование не гарантировано — исключить элемент. Проверить запись до production и учитывать необходимые уведомления/согласия.

Воронки: каталог → взаимодействие; товар → CTA; CTA → checkout; checkout → заказ; заказ → подтверждение; подтверждение → выкуп. Фактические заказы сверять с Supabase, так как блокировщики и ошибки сети могут терять события.

## 15. Meta Pixel + CAPI

Browser/server события дедуплицируются одинаковыми `event_name` и `event_id`. Идентификаторы отправки сохраняются; использовать outbox/retry.

- `PageView` — просмотр страницы.
- `ViewContent` — содержательный просмотр товара, а не просто карточка в DOM.
- `InitiateCheckout` — реальное начало оформления.
- `Purchase` — для COD по умолчанию после подтверждения только если подтверждение действительно означает принятую покупку для оптимизации и это соответствует процессу. Если нет — не отправлять ради увеличения количества конверсий.
- Фактический выкуп хранить отдельно в Supabase; передачу в Meta как поддерживаемую офлайн/серверную конверсию внедрять после проверки актуальной документации, правового основания и дедупликации.

Обновление страницы успеха, повторный webhook и `shipped` не создают повторный Purchase. `purchased` — отдельное внутреннее событие выкупа. Ошибка CAPI не блокирует заказ; retry использует устойчивый ID.

По возможности сохранять UTM, `fbclid`, `_fbp`, `_fbc`, first-touch/last-touch и доступные campaign/ad/creative IDs. Учитывать согласия, ограничения браузеров, блокировщики и неполную атрибуцию. Не передавать PII в URL, события или общие логи без необходимости и правового основания.

## 16. GA4

Дополнительная интеграция. Согласовать ecommerce-события, не дублировать, не отправлять Purchase при каждом просмотре страницы успеха, проверять валюту/сумму/transaction ID. Сверять с Supabase с учётом различий атрибуции.

## 17. Финансовая аналитика

Учитывать фактическую выручку, себестоимость, скидки, расходы магазина на доставку, комиссии, возвраты, прочие переменные расходы и рекламу.

- `Выручка = фактически полученная выручка по выкупленным заказам − возвраты и финансовые корректировки`
- `Маржинальный результат до рекламы = выручка − себестоимость − учитываемые переменные расходы, не учтённые ранее`
- `Прибыль после рекламы = маржинальный результат до рекламы − рекламные расходы`

Не считать невыкупленные заказы полученной выручкой. Неизвестные расходы не считать нулём без предупреждения. Не вычитать расходы дважды.

Отчёты: даты, товары/SKU, источники, кампании/объявления (если доступны), созданные/подтверждённые/выкупленные заказы, отмены, невыкупы, возвраты, выручка, маржа, расходы. Если импорт рекламных расходов не реализован — явно указать отсутствие данных или поддержать ручной импорт.

## 18. CRO и A/B-тесты

Каждый тест имеет гипотезу, контроль, вариант, основную метрику, защитные метрики, критерий завершения и решение. Гипотезы: первый экран, порядок товаров, CTA, sticky CTA, главное фото/порядок фото, цена/подтверждённая скидка, ссылка на детали, поля checkout, доставка, реальные преимущества.

Главные метрики: выкупленные заказы на посетителя и маржинальный результат на посетителя. Дополнительные: подтверждённые заказы, checkout starts, созданные заказы, доли подтверждения/выкупа/отмен, ошибки. Защитные: скорость, дубли, возвраты, невыкупы, средний чек, маржа.

Не объявлять победителя при недостаточной выборке. Учитывать сезонность, кампании, креативы, устройства и состав трафика. Feature flags использовать при необходимости. Эксперимент не должен менять цену, наличие или юридические условия без отдельного утверждения.

## 19. Производительность

Целевые ориентиры: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Это цели для измерения, не гарантия. Оптимизировать изображения, использовать подходящие форматы/размеры, приоритетно грузить главное изображение, lazy-load фото ниже первого экрана, не загружать все медиа сразу, минимизировать клиентский JS, избегать тяжёлых библиотек, предотвращать layout shift, правильно кешировать. Аналитика не должна блокировать checkout.

## 20. Безопасность и приватность

HTTPS, серверная валидация, rate limiting чувствительных операций, защищённая админка, проверка прав, RLS, защита webhook, idempotency, минимизация PII, маскирование логов, аудит и актуальные зависимости.

Секреты (Supabase service-role, Telegram Bot Token, Meta CAPI token, Google service account credentials) — только на сервере и вне Git. Публичный Supabase anon key допустим лишь с корректными политиками. Не логировать телефон, адрес, токены и полный payload без необходимости.

Создать privacy, terms, delivery/payment и returns на основе реальных условий. Не выдумывать реквизиты, гарантии или обязательства. Учесть применимые уведомления и согласия для аналитики/рекламы.

Обработчик блокирует параллельную обработку, считает попытки, использует idempotency, планирует retry, фиксирует окончательные ошибки и не создаёт повторные заказы. ## 30. Итоговый принцип

Google Sheets — исходные данные поставщика. Supabase — опубликованный каталог, заказы и история. Next.js — интерфейс и серверная логика. Telegram — оперативная обработка. PostHog — поведение пользователей. Meta Pixel/CAPI — рекламные конверсии. GA4 при необходимости дополняет аналитику.
